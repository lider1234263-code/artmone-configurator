## 2. Технічна конфігурація

- Статичний односторінковий сайт без framework, package manager, бази даних і серверного backend.
- Основний код: `index.html`, HTML, CSS та JavaScript в одному файлі.
- Поточний `index.html`: 1 903 рядки, 174 749 байтів, SHA-256 `aba78ed1231837821b5251fc772298da1efe83a69a2356ea1951b11717ba2b83`.
- Деплой: GitHub `main` автоматично публікується на Vercel через Git integration.
- Кеш: головна сторінка та `index.html` мають `no-cache, no-store, must-revalidate`; `assets/mockups/*` мають `public, max-age=0, must-revalidate`.
- Каталог: 47 кольорів стрічки у 7 групах.
- Друк: 34 кольори.
- Галерея: 11 фото на колір, thumbnail відкриває головне фото, `+` відкриває lightbox.
- Для відсутнього файла UI показує placeholder.
- Репозиторій має 213 tracked-файлів. У `assets/mockups` є 140 файлів загальним розміром 18 356 090 байтів: 132 нормалізовані файли шести галерей і 7 legacy-файлів AM567, плюс службовий `.gitkeep`.
- У `assets/warehouse` є 49 WebP-фото загальним розміром 580 722 байти.
- `vercel.json` є активним джерелом cache headers для Vercel. `_headers` залишився legacy-файлом з іншою політикою `/assets/*` і потребує окремого рішення.
- Автоматичних тестів і build-step немає. Перевірка виконується статичним аналізом, перевіркою JavaScript/Python syntax, звіркою файлів та live.

### Універсальний стандарт галереї

Для будь-якого коду стрічки використовується одна схема:

- папка: `assets/mockups/am-<код-малими-літерами>/`;
- повні фото: `AMCODE_01.webp` ... `AMCODE_11.webp`;
- мініатюри: `thumbs/AMCODE_01.webp` ... `thumbs/AMCODE_11.webp`;
- повне фото: WebP 1600x1600;
- мініатюра: WebP 320x320;
- приклад: `AM 850` -> `assets/mockups/am-850/AM850_01.webp`;
- приклад з початковими нулями: `AM 009` -> `assets/mockups/am-009/AM009_01.webp`.

`index.html` формує ці шляхи автоматично з AM-коду. Окремо прописувати назви для кожної картки не потрібно.

Після успішного завантаження головного фото обраного кольору решта 10 повних фото цього кольору підвантажуються у фоні. Черга обмежена трьома одночасними запитами, найближчі до поточного фото мають пріоритет, повторні запити у межах сеансу не створюються. Механізм універсальний для всіх 47 кольорів і автоматично працюватиме для кожного нового повного комплекту.

## 4. Обробка наступних кольорів

Скрипт: `scripts/import_gallery.py`.

Він:

1. приймає AM-код і папку з вихідними файлами;
2. вимагає рівно 11 назв `AMCODE_01` ... `AMCODE_11`;
3. нормалізує AM-код, але зберігає значущі нулі, наприклад `AM009`;
4. відхиляє неквадратні джерела;
5. створює 11 WebP 1600x1600 із quality 88;
6. створює 11 WebP 320x320 у `thumbs/` із quality 78;
7. перевіряє формат, розмір і повноту результату;
8. може безпечно повторно перезаписати комплект того самого кольору.

Залежність: `Pillow>=10,<13` у `scripts/requirements-gallery.txt`.

Google Drive connector використовується для читання оригіналів. Скрипт обробляє отриманий локальний комплект. Поточний фактичний pipeline: `Google Drive -> локальна перевірка/імпортер -> GitHub main -> автоматичний Vercel deploy`. Це повторюваний керований процес, але не автономний watcher і не прямий автоматичний імпорт із Pletor.

## 7. Невирішені питання

### P0

1. Ще 41 колір не має нового повного комплекту з 11 фото та 11 мініатюр.
2. Кнопки замовлення й контакту не передають заявку менеджеру.
3. `Надіслати прорахунок собі` лише пише контакт у `localStorage`.
4. `Потрібна допомога з вибором?` лише показує toast.

### P1

1. Google Drive -> GitHub наразі виконується керовано через підключений Drive і скрипт, а не постійним фоновим watcher.
2. У репозиторії досі лежать `assets/import/bundle.zip`, чотири `chunk_*.txt` і workflow `.github/workflows/import-gallery-zips.yml`; workflow очікує 13 chunks, хоча tracked лише 4, тому цей механізм фактично мертвий.
3. Workflow `.github/workflows/unpack-am1-gallery.yml` посилається на вже видалений ZIP. Інші patch-workflows залишаються одноразовими legacy-автоматизаціями та не є тестами або актуальним pipeline.
4. AM567 legacy-галерею треба замінити повним новим комплектом із 11 квадратних оригіналів. Не генерувати відсутні фото.
5. `manifest.json` має застарілі твердження про `v16-static-prebuilt`, 7 scenes і 11 186 prebuilt images. `README_TECH_ONLY_UA.txt` уже позначає себе як legacy, але може бути видалений після підтвердження.
6. `_headers` суперечить `vercel.json` щодо кешування assets; для поточного Vercel live фактично діє `vercel.json`.

### P2

1. Немає автоматичних browser/E2E тестів калькулятора, мобільного UI та lightbox.
2. Код і стилі залишаються в одному великому `index.html`.
3. Vercel connector не повертає team/project ID; production перевірено через публічний live і точні хеші файлів.

## 8. Точний наступний крок

Зробити один окремий технічний cleanup-коміт без зміни `index.html` і бізнес-логіки:

1. видалити `assets/import/bundle.zip` і `assets/import/chunk_00.txt` ... `chunk_03.txt`;
2. видалити мертві workflows `import-gallery-zips.yml` та `unpack-am1-gallery.yml`;
3. перевірити інші одноразові patch-workflows і залишити лише ті, які справді ще потрібні;
4. оновити або видалити застарілі `manifest.json`, `_headers` і `README_TECH_ONLY_UA.txt` так, щоб вони не суперечили `PROJECT_CHECKPOINT.md` і `vercel.json`;
5. виконати syntax/static перевірки, commit/push у `main`, дочекатися Vercel і повторно звірити live.

Після cleanup наступний контентний етап: отримати 11 квадратних оригіналів для AM567, імпортувати їх через `scripts/import_gallery.py` і лише тоді прибрати сім legacy-файлів AM567.
